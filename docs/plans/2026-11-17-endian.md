# SAV byte-order implementation plan

> Execute inline using superpowers:executing-plans; user “下一步” continues the documented stage2. Existing PLAN.md authorizes direct execution. Preserve owner-maintained acceptance/submission files; no public push/release/registration.

**Goal:** Read modern IEEE754 SAV/ZSAV with either big- or little-endian integers and matching floats, preserving all existing semantics and source byte order in metadata. This milestone does not complete IBM26 compatibility.

**Architecture:** Select order once from layout_code bytes at64. A single Cursor propagates it to every i32/u64/f64 read and nested extension cursor; Dictionary retains byte_order and uses it for numeric atoms, literal slots and ZSAV directories. Generated compression integers must be encoded in that same order before row decoding. Text/bytecode control bytes/string keys are never swapped.

**Spec:** docs/COMPATIBILITY_TARGET.md stage2; GNU PSPP System File Format (Introduction/Header/Machine Integer Info/Data Record), https://pspp.benpfaff.org/manual/system-file.html .

## Decisions and constraints

- Keep the existing user-designated standalone checkout and inline method. Baseline6654d47; only preexisting untracked submission/acceptance/log directories. No tracked source changes at start.
- Add public Dictionary.byte_order:String (little/big) and preserve it in metadata, codebook, types/schema and checker. Older bundles without the field default to little because every previously supported file was little-endian. Wrong field values reject; they cannot alter canonical numeric bits.
- Integer and IEEE754 float order must agree for this milestone. Machine record declaring an order that contradicts layout is InvalidDictionary. Explicit non-IEEE representation remains UnsupportedFloat. A reversed standard100 bias indicates unsupported mixed-order floats and must fail rather than silently invent values. Arbitrary nonstandard mixed-order producers remain unproven; do not claim them.
- Public hex numeric bits are order-independent; raw string/label bytes remain source bytes. Source-order raw extra metadata can legitimately differ across orders, unlike interpreted semantics.
- Use independent development-only Python format conversion of synthetic ReadStat/known vectors to generate big-endian forms, not a product parser/writer or fake IBM producer. Validate the converted files independently through ReadStat and PSPP.
- Keep all limits and strict errors, including existing ZSAV adapters. Native/wasm-gc still require a caller inflater for ZSAV data; uncompressed/bytecode endian reads work directly on all three backends.

## Review focus

1. Header changes alone must not make unswapped dictionary/data look valid.
2. Numeric user-missing/labels/sentinels and bytecode-generated integers must agree with literal numeric reads; string bytes/keys must remain unchanged.
3. Nested extension11/16/21/22 integer lengths and ZSAV64-bit offsets need the same order.
4. Unknown/contradictory layout, truncated and overflowing big-endian lengths must reject within limits and failed exports must not commit.
5. Exported big-endian bundle semantics, old missing-byte_order bundles and installed packages must pass the real checker/consumer rather than just schema validation.
